# rules.md 生成模板

> 用途：brain-workflow skill 初始化时，以本文件为底稿生成项目自己的 `brain/rules.md`。
> 使用前必做：① 在「引用纪律」处填入用户指定的事实引用源；② 若项目已有工单系统，在 §2 末尾补充边界声明；③ 按项目语言习惯微调措辞。生成后删除本提示块。

# brain/ 交互规则

## 1. 这个文件夹是什么

`brain/` 是**用户与 AI 在本项目内的长期协作空间**，存放思考、决策与交互约定。

**流转链路**（一一对应，全程锚点可追溯）：

```
thoughts/（想法，每想法一个 md，命名 thoughts-YYMMDD-HHMMSS.md）
   │ 用户拍板
   ▼
decisions.md（一行一句，[thoughts-YYMMDD-HHMMSS] 锚点唯一对应）
   │ 方案展开
   ▼
plans/（计划文档 plans-YYMMDD-HHMMSS.md，与 thoughts 同一时间戳命名）
   │ 按计划开发
   ▼
用户确认完成
   ▼
thoughts md → archive/thoughts/；plans md → archive/plans/
```

## 2. 文件职责

| 文件 | 内容 | 写入者 |
| --- | --- | --- |
| `thoughts/` | 用户的想法与需求；AI 在条目下追加评语与完成进度 | 用户写条目，AI 追加区块 |
| `plans/` | 拍板决策展开后的开发计划，每个决策一份 | AI 起草，用户确认 |
| `decisions.md` | 记录用户拍板的决策及其执行状态；**状态的唯一权威源** | 用户拍板后 AI 更新 |
| `rules.md` | 本文件夹内的交互规则（即本文件） | 双方，以用户为准 |
| `archive/` | 已结束条目的归档（含 `archive/thoughts/`、`archive/plans/`） | AI 归档，用户可撤回 |

以后如新增文件，需在本表登记职责，避免职责漂移。

**引用纪律**：（填入本项目事实引用源，如 codegraph 知识图谱 / 权威文档 / 数据契约文件；引用源未覆盖的，当场实测后补录，不得凭记忆或旧日志给数。）

**与工单系统的边界**（如有）：`brain/` 管"为什么做、做什么、是否做完"；工单系统管"执行分派与排期"。计划中的可分派步骤进入工单时，在 plans 文档中注明工单号。

## 3. thoughts 条目格式

一想法一个 md，新建 `brain/thoughts/thoughts-YYMMDD-HHMMSS.md`（同秒冲突时秒数 +1）：

```markdown
## [YYMMDD-HHMMSS] 标题

- 提出时间：YYYY-MM-DD
- 状态：未开始

（用户的想法正文，忠实记录，不改写）

### AI 评语

> YYYY-MM-DD

（AI 的判断、风险、建议，先结论后展开）

### 进度

- [ ] 待办动作
```

状态词表（固定）：`未开始` / `评估中` / `进行中` / `已完成` / `搁置` / `待澄清`。
thoughts 的状态是镜像，冲突以 decisions.md 为准。

## 4. decisions.md 条目格式

- **一句话原则**：每个决策写成一句可独立读懂的话，只写"拍板了什么"；细节回 thoughts 条目查看。
- **唯一对应**：一条决策对应且仅对应一个 thoughts 条目，句末以 `[thoughts-YYMMDD-HHMMSS]` 锚点注明出处。无对应 thoughts 条目的拍板，先补建 thoughts 条目再登记。同一想法的后续拍板更新原句，不新增条目。
- **锚点解析**：锚点按 `thoughts/` → `archive/thoughts/` 的顺序解析；文件归档移动后**不修改锚点**。
- **状态前置 + 三分区**：条目以状态词开头，文件按 `## 未开始的决策` / `## 进行中的决策` / `## 历史决策` 三区块组织。
- **唯一权威状态源**：decisions.md 是状态的唯一权威；thoughts / plans 中的状态仅是镜像，冲突以本文件为准。
- **简洁纪律**：全文件保持一屏可读完；条目进入「历史决策」后措辞不再改动。
- **历史膨胀控制**：历史决策条目超过 30 条时，AI 提议将已归档任务对应的条目迁出至 `archive/decisions-history.md`（按年份分节），原位置留一行指针。
- **计划衔接**：决策进入「进行中」前，应先在 `plans/` 建立对应计划文件。

条目格式：

```markdown
- [状态] 一句话决策描述 [thoughts-YYMMDD-HHMMSS]
```

## 5. plans 条目格式

决策拍板且需要开发时，新建 `brain/plans/plans-YYMMDD-HHMMSS.md`（时间戳与对应 thoughts 条目一致）：

```markdown
## [YYMMDD-HHMMSS] 标题

- 创建时间：YYYY-MM-DD
- 对应决策：[thoughts-YYMMDD-HHMMSS]
- 状态：进行中

### 目标

（一句话说清要达成什么）

### 方案

（展开的实施步骤 / 设计要点，按可执行粒度编号）

### 验收标准

- [ ] 可验证的完成条件
```

- 计划由 AI 起草，**用户确认后方可按计划开发**。
- 进度在计划「验收标准」与 thoughts 条目「进度」中同步勾选；状态以 decisions.md 为准。
- 计划变更直接改文档，文末追加变更记录（日期 + 一句话）；重大变更需用户确认。

## 6. AI 的行为约定

1. **先读后写**：每次进入本文件夹的会话，先读 `rules.md` 再动手。
2. **不改动用户原文**：AI 只在 thoughts 条目下方追加区块；修正用户原意应在评语中指出。
3. **先结论后展开**：评语首句给判断，再给理由。
4. **不编造事实**：按「引用纪律」查证后给出数据；无法核实时明说"未核实"。
5. **进度可审计**：用清单勾选，不写"基本完成"这类模糊表述。
6. **含糊指令不自动延续**：用户说"继续""你看着办"时，先停下确认，不自主推进外部动作。
7. **外部动作需显式确认**：git 提交/推送、改数据文件、对外发布，先列变更清单等用户确认。
8. **archive 默读禁入**：除非用户显式要求查阅 `archive/` 内容，AI 不阅读该文件夹内任何文件。
9. **工作流自进化**：用户对规则的调整若具有通用性，AI 提议反向同步回 brain-workflow skill。

## 7. 归档规则

- **触发**：任务**经用户确认完成**（decision 状态为 `已完成`）后，AI 提议归档；AI 不得因开发结束自行归档。
- **双份动作**：
  1. thoughts 条目移入 `archive/thoughts/`，文末留一行 `> 已归档至 archive/thoughts/`
  2. plans 文档移入 `archive/plans/`，文末留一行 `> 已归档至 archive/plans/`
  3. decisions.md 中该条已在「历史决策」区块，措辞不动，锚点不改
- 归档由 AI 提议、**用户确认后执行**；归档不删除内容，随时可撤回。
- 搁置的决策**不归档**，留在 decisions.md 原区块（状态 `搁置`），待重启后再处理。
